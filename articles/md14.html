为什么要做这个

写完一个前端页面之后，我习惯先看一眼「到底长什么样」再交付。

传统做法是让人打开浏览器瞄一眼。但有两个问题：

  1. 人工检查不稳定 —— 这次看了，下次改完还得再看
  2. 不同尺寸的适配没法逐个人工验 —— 桌面 880px、手机 414px、平板 768px，一个个手动缩放太累

于是想用无头浏览器 + 截图做自动化验证：跑一条命令，出一张图，直接看渲染结果。

方案：用系统自带的浏览器，不装任何依赖

第一反应是 Puppeteer / Playwright。但这两个都要下载 Chromium（500MB 左右），为了截个图装这么大一坨不太值。

Windows 上有个现成的选择：Edge。

EDGE = r"C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"

args = [
    EDGE,
    "--headless=new",              # 无头模式
    "--disable-gpu",
    "--no-sandbox",
    "--hide-scrollbars",           # 隐藏滚动条，截图更干净
    "--virtual-time-budget=8000",  # 虚拟时间预算，等页面渲染
    "--window-size=880,1500",      # 视口尺寸
    "--screenshot=out.png",        # 输出路径
    url,
]

subprocess.run(args, timeout=120)

跑完直接得到一张 PNG。 不需要 npm、不需要 pip install、不需要下载浏览器。

Chrome 的路径也一样：

CHROME = r"C:\Program Files\Google\Chrome\Application\chrome.exe"

关键参数解释

`--headless=new`

无头模式。注意要用 `new`，旧的无头模式（`--headless`）在新版浏览器里已经废弃了。

`--virtual-time-budget`

这个参数最容易踩坑。

它的作用是：让浏览器在「虚拟时间」内尽量跑完页面逻辑，然后截图。单位是毫秒。

  • 值太小 → 页面还没渲染完就截图，得到空白页
  • 值太大 → 等待时间长

我的经验值：

  • 纯静态页面：`3000`
  • 有异步请求的页面：`8000`
  • 有大量网络请求的页面：`15000-20000`

注意：虚拟时间不是真实时间。它让定时器「快进」，但不会真的等网络请求返回。如果页面依赖外部网络，可能还是截不到。

让页面「自己动」：注入驱动脚本

截静态页面很简单，但我想验证的是交互后的状态（比如搜索结果列表）。

做法：造一个临时页面，在原页面基础上注入一段自动执行的脚本。

src = open("page.html", encoding="utf-8").read()

AUTO = """
<script>
(async function(){
  await new Promise(r => setTimeout(r, 600));
  document.getElementById('q').value = '关键词';
  document.getElementById('go').click();      // 自动点搜索
})();
</script>
"""

# 把脚本插到 </body> 之前
tmp = src.replace("</body>", AUTO + "</body>")
open("page_auto.html", "w", encoding="utf-8").write(tmp)

然后截 `page_auto.html`，就能拿到「搜索后」的状态。

踩坑：临时页面被 404

这是我在这个方案上唯一卡住的地方。

我一开始把临时页面写成 `_auto.html`，放在服务目录下，然后访问 `http://127.0.0.1:8099/_auto.html`。

结果：404。

原因是：我的服务只对白名单里的文件名提供访问。

def do_GET(self):
    path = urlparse(self.path).path
    if path in ("/", "/index.html", "/finder.html"):
        return self.serve_file("finder.html")
    if path == "/manifest.json":
        return self.serve_file("manifest.json")
    # ... 其他白名单 ...
    return self._json({"error": "not found"}, 404)   # 其他一律 404

这个设计本身是对的——限制暴露面，不应该什么文件都能访问。但它导致我随便丢个临时文件进去，服务不认。

解决办法：临时替换 + 用完还原

不用新增路由，直接覆盖原页面文件，截完再还原：

import shutil

target = "finder.html"
backup = "finder.html.bak"

shutil.copy2(target, backup)          # 1. 备份原文件
try:
    open(target, "w", encoding="utf-8").write(注入版内容)
    shot("preview.png")               # 2. 截图
finally:
    shutil.move(backup, target)       # 3. 无论如何都还原

用 `try/finally` 保证还原——哪怕截图失败，原文件也不会被留在被覆盖的状态。

另一个坑：页面里的网络请求

如果页面加载时要调接口，而接口本身很慢（比如要几十秒），那截图时页面还是空的。

我的做法是「拦截请求，喂假数据」：在注入的脚本里劫持 `fetch`：

window.__DEMO__ = { /* 预先取好的真实数据 */ };

(function(){
  const origFetch = window.fetch;
  window.fetch = function(url, opt) {
    if (String(url).indexOf('/api/search') === 0) {
      // 搜索接口直接返回预取的数据，不走网络
      return Promise.resolve({ json: () => Promise.resolve(window.__DEMO__) });
    }
    return origFetch(url, opt);     // 其他请求照常
  };
  // 然后触发搜索
  document.getElementById('go').click();
})();

注意 `window.__DEMO__` 里塞的是「预先用真实接口取好的数据」——这样截出来的图跟真实效果一致，又能避开等待。

多尺寸验证

同一套代码，换个 `--window-size` 就能验证不同设备：

shot("desktop", w=880,  h=1500)   # 桌面
shot("mobile",  w=414,  h=950)    # iPhone 尺寸
shot("tablet",  w=768,  h=1024)   # iPad 尺寸

我的习惯是先看桌面版，再看 414px。 414px 是最窄的常见手机宽度，能在这里不溢出，基本就没问题。

实测结果

用这套方案验证了一个列表页：

检查项结果
桌面版（880px）✅ 内容完整，无溢出
手机版（414px）✅ 布局正常折行
外部图片加载✅ 全部正常
交互后状态✅ 成功触发并截取

整个过程不到 10 秒（不含页面本身的网络等待）。

三条经验

第一，能用系统浏览器就别装 Playwright。

Edge / Chrome 的 `--headless=new` 已经能覆盖大部分截图需求。只在需要复杂交互（多步点击、表单填写、Cookie 管理）时才考虑上 Playwright。

第二，注入脚本比手动操作可靠。

「打开页面 → 手动点按钮 → 截图」这种流程没法自动化。把操作写进注入的脚本里，一条命令跑完全程。

第三，临时文件用完一定要还原，而且要用 `try/finally`。

我覆盖 `finder.html` 做演示的时候，如果中途抛异常没还原，服务就会一直返回演示版页面——这是很危险的状态。`try/finally` 是底线。
