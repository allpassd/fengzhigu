起因

我在本地维护了一个自建的电子书阅读服务，书库放在 `E:\books`，支持 EPUB/TXT，能翻页能听书。用了一段时间之后发现一个问题：书得自己找、自己放进去，没有一个顺手的下书渠道。

于是想接一个电子书源的命令行工具，做成「搜书 → 下载 → 自动进书库」的闭环。

第一回合：手工猜域名，全军覆没

这类站点的域名经常换，我第一反应是「手工试几个」。

于是写了个脚本，把能想到的域名挨个测 TCP 连通性：

import socket

domains = ["z-lib.org", "zlibrary.to", "1lib.to", ...]  # 一共 31 个

for d in domains:
    try:
        s = socket.create_connection((d, 443), timeout=5)
        print("通", d)
        s.close()
    except Exception:
        print("不通", d)

结果：31 个域名，全部不通。

到这里其实就该停下来想想了。但我又试了第二轮——换成测 HTTP 层：

import urllib.request

for d in domains:
    try:
        r = urllib.request.urlopen("https://" + d, timeout=8)
        print(r.status, d)
    except Exception as e:
        print("ERR", d, e)

结果依然是全军覆没，要么连接超时，要么直接报 DNS 解析失败。

这时候我意识到问题所在了：我在用「我以为存在的域名」去试探，但这些域名可能早就废弃了。与其继续猜，不如找一个维护着最新域名列表的工具。

第二回合：装工具，让它自己报可用域名

找到了一个用 Go 写的命令行客户端（开源项目，支持搜索、下载、历史、配额查询）。下载二进制、跑起来。

它有个 `doctor` 子命令，功能是探测当前可用的镜像域名：

zlib.exe doctor --eapi

跑完输出让我有点意外：

zlib.bz      → healthy
zliba.ru     → challenged

两个可用的域名，都不在我手工猜的那 31 个里面。

这就是典型的「信息差」问题：

  • 我在用记忆里的域名试探
  • 工具在维护实际在用的域名列表

工具的列表更新更快、更准。手工猜的命中率基本为零。

关于「challenged」状态

输出的 `challenged` 这个状态值得一提。

它的含义是：域名是活的，但返回了一个浏览器挑战页（HTTP 503）。 这是反爬机制——服务器先给你一个需要执行 JS 才能通过的页面，通过之后才放行真正的请求。

zlib.bz     → healthy        直接可用
zliba.ru    → challenged     需要过挑战页，工具会自动处理

这里有个重要的判断标准：能用不能用，要看 HTTP 层，不能只看 TCP。

我第一轮测 TCP 的结果里，有几个域名 TCP 是通的，但实际返回的是挑战页或者错误页。如果只看「端口通不通」，会得出完全错误的结论。

第三回合：验证全链路

域名通了，接下来验证完整流程。

登录：

zlib.exe login --eapi

成功。凭证会缓存在本地配置目录，之后不用重复登录。

搜索测试（用「三体」）：

zlib.exe search "三体"

返回 50 条结果，中文书完整，格式、大小、评分都有。这一步验证了网络、认证、解析三层都正常。

下载测试：

zlib.exe download "26610712:def1ec" -d "E:\books"

下载下来 2,600,699 字节。校验一下完整性——EPUB 本质是 zip，用 zipfile 打开看看能不能正常解析：

import zipfile
z = zipfile.ZipFile(r"E:\books\三体.epub")
print(len(z.namelist()), "个文件")   # 110 个文件

110 个文件，元数据正常，书名作者都对。链路完全可用。

踩到的几个小坑

坑一：参数名不是想当然的那个

zlib.exe download "xxx" -o "E:\books"    # ❌ 报错 unknown shorthand flag: 'o'
zlib.exe download "xxx" -d "E:\books"    # ✅ 正确

指定下载目录用 `-d`（directory），不是 `-o`（output）。

坑二：查配额的命令名

zlib.exe quota      # ❌ unknown command "quota"
zlib.exe profile    # ✅ 正确

没有 `quota` 这个命令，配额查询在 `profile` 里。

坑三：Windows 批处理文件不能有中文

这个坑踩得最狠。

我一开始写了个桌面快捷脚本，文件名叫 `下书.bat`，内容是：

@echo off
set BOOKS_DIR=E:\books
echo 下载目录：%BOOKS_DIR%
zlib.exe search %*

在 GBK 环境下，这个文件被完全解读错了。 报错长这样：

'ず渚嬶細涓嬩笅鍔?bat' 不是内部或外部命令
'BOOKS_DIR' 不是内部或外部命令

文件名和内容里的中文全部变成乱码，把命令结构冲散了。

原因：Windows 批处理文件按系统本地编码（中文系统是 GBK）读取，如果文件内容里混了中文，读写编码不一致就会乱码。

解决办法：批处理文件全部用纯 ASCII——文件名用英文，内容也用英文，中文只作为参数传入：

@echo off
set BOOKS_DIR=E:\books
zlib.exe search %*

调用时中文作为参数：

book.bat "三体"

这样中文走的是命令行参数，不经过文件编码，就没问题了。

闭环成立：搜书 → 下载 → 入库 → 阅读，全程打通。

三条经验

第一，别用记忆猜服务地址。

这类站点的域名变动频繁，靠印象去试基本是浪费时间。找一个维护着列表的工具，让它自己探测。

第二，TCP 通不等于能用。

第一轮我测 TCP 的时候，有几个域名端口是通的，但 HTTP 层返回的是挑战页。要判断「能不能用」，必须走到 HTTP 层看实际响应。

第三，Windows 下的批处理要谨慎对待中文。

这个坑不在于「会不会乱码」，而在于乱码之后的表现极具迷惑性——命令被拆碎了报一堆看不懂的错，很容易以为是别的问题。规则很简单：批处理文件保持纯 ASCII。

本文记录的是实际调试过程，所有命令行输出和错误信息都来自真实测试。
