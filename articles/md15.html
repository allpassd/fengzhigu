起一个本地 HTTP 服务，第一反应通常是装 Flask。但用 WorkBuddy 折腾下来发现，只需求几个接口的话，Python 标准库就够了，一个依赖都不用装。
本文属于 WorkBuddy 实战笔记系列。

为什么要用标准库

`pip install flask` 只要一行，为什么要费劲用标准库？

几个真实场景：

  1. 目标机器上不一定能装包 —— 离线环境、受限网络、或者不想在系统里留痕迹
  2. 依赖越少越稳 —— 几十行代码的小服务，不需要一个框架
  3. 启动快、包体积小 —— 不用等依赖解析

Python 的 `http.server` 一直被当成「只能做 demo」的玩具，但实际上加几行就能做到：并发处理、JSON 接口、流式返回文件。 这篇文章记录我实际怎么做。

最小可运行版本

import http.server, json

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/api/ping":
            body = json.dumps({"ok": True}).encode("utf-8")
            self.send_response(200)
            self.send_header("Content-Type", "application/json; charset=utf-8")
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)

if __name__ == "__main__":
    http.server.HTTPServer(("127.0.0.1", 8000), Handler).serve_forever()

五行核心逻辑就够了。 但直接拿去用会踩几个坑。

坑一：单线程，一个慢请求阻塞全部

`HTTPServer` 是单线程的。如果一个请求要处理 30 秒，第二个请求必须排队等。

这在浏览器里表现得很明显：页面上的多个请求会串行执行，看起来像卡死。

解决办法：换成多线程版本。

import socketserver

class ThreadingServer(socketserver.ThreadingMixIn, http.server.HTTPServer):
    daemon_threads = True        # 主线程退出时，子线程跟着结束
    allow_reuse_address = False  # 见下面「坑二」

http.server.HTTPServer = ThreadingServer   # 或者直接用 ThreadingServer 实例化

`ThreadingMixIn` 让每个请求在独立线程里处理。加上 `daemon_threads = True`，主进程退出时不会因为还有活跃线程而挂住。

坑二：端口被「幽灵占用」

调试时经常遇到这个：

OSError: [WinError 10048] 通常每个套接字地址只允许使用一次

原因通常是：

  1. 上一个进程还在跑
  2. 或者处于 `TIME_WAIT` 状态（连接已关闭但端口还没释放）

标准做法是设 `allow_reuse_address = True`（`SO_REUSEADDR`），让系统允许复用这个端口。

但这里有个权衡。 在某些平台上，`SO_REUSEADDR` 允许两个进程绑定同一个端口，导致请求被随机分发到不同进程——排查起来极其痛苦。

我的选择是显式设为 `False`：

class ThreadingServer(socketserver.ThreadingMixIn, http.server.HTTPServer):
    daemon_threads = True
    allow_reuse_address = False   # 宁可报错，也不要「幽灵双绑」

宁可启动时明确报错，也不要默默跑着两个实例。 报错了你至少知道要先停掉旧的。

坑三：`log_message` 在无控制台环境下崩溃

这是最隐蔽的一个，我卡了很久。

服务在测试时跑得好好的，一旦改成后台无声启动（pythonw / 无控制台），就变成「每个请求必崩」。

原因在这里：

class BaseHTTPRequestHandler:
    def log_message(self, fmt, *args):
        sys.stderr.write("%s - - [%s] %s\n" % (...))   # ← 这里

标准库的实现会往 `sys.stderr` 写日志。但在 pythonw 或无控制台环境下，`sys.stdout` 和 `sys.stderr` 都是 `None`。

于是：`None.write(...)` → `AttributeError` → 每个请求都在日志阶段抛异常，客户端看到的是连接被无响应关闭。

解决办法一：重写 `log_message`

def log_message(self, fmt, *args):
    try:
        sys.stderr.write("[%s] %s\n" % (self.log_date_time_string(), fmt % args))
    except Exception:
        pass       # 日志失败绝不能影响业务

关键点是 `try/except` —— 日志是附属功能，绝不能让它影响主流程。

解决办法二：启动时兜底流

if sys.stdout is None:
    sys.stdout = open(os.devnull, "w", encoding="utf-8")
if sys.stderr is None:
    sys.stderr = open(os.devnull, "w", encoding="utf-8")

两个一起用最稳。 兜底流处理「没控制台」的情况，`try/except` 处理「流存在但写入失败」的情况。

还有一个相关的坑：编码

如果输出被重定向到管道或文件，`sys.stderr` 的编码可能是系统本地编码（中文系统是 GBK）。 这时日志里如果有 emoji 或者特殊字符，会抛 `UnicodeEncodeError`。

try:
    sys.stdout.reconfigure(encoding="utf-8", errors="replace")
    sys.stderr.reconfigure(encoding="utf-8", errors="replace")
except Exception:
    pass

统一改成 UTF-8 并加 `errors="replace"`，保证任何字符都不会导致写入失败。

关键点一：文件流式返回

不要把整个文件读进内存再发。 大文件会吃满内存。

def _send_file_stream(self, path, mime):
    size = path.stat().st_size
    self.send_response(200)
    self.send_header("Content-Type", mime)
    self.send_header("Content-Length", str(size))    # 必须带，否则浏览器不知道进度
    self.end_headers()
    with open(path, "rb") as fh:
        while True:
            chunk = fh.read(65536)                    # 64 KB 一块
            if not chunk:
                break
            self.wfile.write(chunk)

`Content-Length` 一定要带，否则浏览器无法显示下载进度，也可能不显示「另存为」。

关键点二：路径安全（很重要）

如果服务要读文件，必须防路径穿越。

用户请求 `/files/../../etc/passwd` 这种，如果不处理，就可能读到不该读的文件。

我的做法是用白名单，而不是拼接路径：

def do_GET(self):
    path = unquote(urlparse(self.path).path)

    if path in ("/", "/index.html"):
        return self.serve_file("index.html")      # 只从固定目录取指定文件
    if path.startswith("/api/cover/"):
        return self.api_cover(path.rsplit("/", 1)[-1].split("?")[0])   # 只取文件名部分
    return self._json({"error": "not found"}, 404)

两个要点：

  1. 用白名单匹配，不用「拼接用户输入到根目录」
  2. 取路径最后一段作为文件名，天然过滤掉 `../`

这个设计还有个副作用（后面提到的踩坑）：因为太严格，我自己丢进去的临时文件也会被 404。

关键点三：JSON 响应的统一封装

每个接口都手写 header 太啰嗦，封装一下：

def _json(self, obj, status=200):
    body = json.dumps(obj, ensure_ascii=False).encode("utf-8")
    self._send_bytes(status, "application/json; charset=utf-8", body)

def _send_bytes(self, status, ctype, data):
    self.send_response(status)
    self.send_header("Content-Type", ctype)
    self.send_header("Content-Length", str(len(data)))
    self.send_header("Cache-Control", "no-store")          # 接口不缓存
    self.send_header("Access-Control-Allow-Origin", "*")   # 需要跨域时加
    self.end_headers()
    try:
        self.wfile.write(data)
    except Exception:
        pass         # 客户端提前断开时不报错

`ensure_ascii=False` 很关键——不然中文会变成 `\u4e2d\u6587` 这种转义序列，虽然合法但可读性差。

`wfile.write` 包 `try/except`：客户端可能中途关闭连接（比如用户刷新页面），这时写入会抛异常。这不是服务的问题，不该让它污染日志。

启动横幅：把访问地址打出来

服务跑起来之后，用户最需要知道的是「从哪访问」。启动时打印清楚：

lan = get_lan_ip()
print("=" * 56)
print("  服务已启动")
print("=" * 56)
print(f"  本机    : http://127.0.0.1:{PORT}/")
print(f"  局域网  : http://{lan}:{PORT}/")
print("=" * 56)
print("  按 Ctrl+C 停止")

取值方式用 UDP 探测，不要解析 `ipconfig`：

def get_lan_ip():
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    try:
        s.connect(("8.8.8.8", 80))    # 不发包，只让系统选路由
        return s.getsockname()[0]
    finally:
        s.close()

为什么不用 `ipconfig`：输出是本地编码（中文系统 GBK），解析要处理编码问题；而且多网卡时输出很复杂。UDP 探测一行搞定，还更准。

完整骨架

把上面这些拼起来：

import http.server, socketserver, json, socket, os, sys
from pathlib import Path
from urllib.parse import unquote, urlparse

ROOT = Path(__file__).parent
PORT = 8099

class Handler(http.server.BaseHTTPRequestHandler):

    def log_message(self, fmt, *args):
        try:
            sys.stderr.write("[%s] %s\n" % (self.log_date_time_string(), fmt % args))
        except Exception:
            pass

    def _json(self, obj, status=200):
        self._send_bytes(status, "application/json; charset=utf-8",
                         json.dumps(obj, ensure_ascii=False).encode("utf-8"))

    def _send_bytes(self, status, ctype, data):
        self.send_response(status)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(data)))
        self.send_header("Cache-Control", "no-store")
        self.end_headers()
        try:
            self.wfile.write(data)
        except Exception:
            pass

    def do_GET(self):
        path = unquote(urlparse(self.path).path)
        if path in ("/", "/index.html"):
            return self.serve_file("index.html")
        if path == "/api/info":
            return self._json({"port": PORT, "lan": get_lan_ip()})
        return self._json({"error": "not found"}, 404)

    def serve_file(self, name):
        f = ROOT / name
        if not f.exists():
            return self._send_bytes(404, "text/plain; charset=utf-8", b"not found")
        self._send_bytes(200, "text/html; charset=utf-8", f.read_bytes())


class Server(socketserver.ThreadingMixIn, http.server.HTTPServer):
    daemon_threads = True
    allow_reuse_address = False


def get_lan_ip():
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    try:
        s.connect(("8.8.8.8", 80))
        return s.getsockname()[0]
    finally:
        s.close()


def serve():
    os.chdir(ROOT)
    # 无控制台环境兜底
    if sys.stdout is None:
        sys.stdout = open(os.devnull, "w", encoding="utf-8")
    if sys.stderr is None:
        sys.stderr = open(os.devnull, "w", encoding="utf-8")
    for s in (sys.stdout, sys.stderr):
        try:
            s.reconfigure(encoding="utf-8", errors="replace")
        except Exception:
            pass

    lan = get_lan_ip()
    print(f"  本机   : http://127.0.0.1:{PORT}/")
    print(f"  局域网 : http://{lan}:{PORT}/")

    Server(("0.0.0.0", PORT), Handler).serve_forever()


if __name__ == "__main__":
    serve()

这就是一个能实际用的骨架：支持并发、无控制台可用、路径安全、JSON 接口、文件服务。

三条经验

第一，日志失败绝不能影响业务。

`log_message` 里那个 `try/except` 是最重要的一行。在无控制台环境下，它决定了服务是「正常跑」还是「每个请求必崩」。

第二，`allow_reuse_address` 要慎重。

默认的 `True` 在某些平台上允许端口被两个进程同时绑定，问题极难排查。宁可启动时报错，也不要默默跑着两个实例。

第三，路径处理用白名单，不要拼接。

「把用户输入拼到根目录」是最常见的路径穿越漏洞来源。用白名单匹配已知路径，取文件名时只用最后一段。
